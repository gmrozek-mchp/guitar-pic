## Current focus

**Phase 3 done — the model plays hard mode standalone on the fretboard MCU. Read this first to resume cold.**

End-to-end works: a 16-channel int8 StrumNet, distilled from marvin's hard-mode play across 5 songs, runs standalone on the PIC32CM (no marvin), reads its own photosensors, and drives the controller — playing hard reasonably well on the bench. Deploy model: `--channels 16 --window 85 --no-holdout --strum-weight 5 --epochs 50` (dilations `(1,4,16)`, RF 85 — **`--window 85` is required, it must be ≥ RF or the streaming engine won't build**), quantised at `--strum-thresh 0.80 --strum-hold 8 --strum-refractory 8`. Inference in the main loop (not the ISR), 240 Hz sampling, SW0/LED enable toggle.

Difficulty target was **hard** first (all 5 frets, slower scroll). **Open next-steps under discussion** (2026-06-04): residual-lag lead-comp, per-difficulty models, and a **2-sensor-per-fret hardware** revision (see open questions). Known caveats: slight overstrum remains (threshold-tunable); play quality not yet scored against a baseline (rollout Phase 5).

## Open questions

> Phase-1-blocking items first; the design forks for phase 2+ live in [`review.md`](review.md).

- **[Future hardware — user wants to pursue] 2 photosensors per fret channel (like the CV detector).** Add a second sensor per fret so each channel sees two points along the note's travel (à la marvin's CV detector). Implications: input grows 5→10 channels (`MODEL_N_IN`, the input ring, the input affine — all parameterised already, but the trained model + `model_weights.h` change); two sensors per fret give the model an explicit *velocity/approach* signal (a note dimming sensor A then B encodes speed + direction), which should sharpen onset timing and could reduce the photo→strum lag ambiguity — possibly even let one model span difficulties (relates to the deferred scroll-speed-sensor idea below). Needs: fretboard HW revision (10 ADC inputs / channel mux), a fret_scan update, a wire-format/`FretboardRaw` bump for 10 channels, re-capture the corpus on the new HW, retrain. Big change; the current 5-sensor model is the baseline it must beat. **Discuss scope before building.**

- **[Open follow-up] Red fret is the lone laggard (held-out .890 vs ≥.96 for the others).** Consistent across epochs and was joint-weakest in overfit too, so it's real, not noise. *Not* a corpus-coverage gap — slowride red density (26 %) is mid-pack vs the training songs (24–30 %). Hypotheses to test: (a) single-holdout variance — **rotate the holdout** across all five songs and see if the weak fret tracks the song (variance) or stays red (systemic); (b) neighbour confusion — red sits between green/yellow, so check red's false-positives/negatives against green/yellow activity; (c) `ph_red` channel quality (saturation/standardisation stats). Cheapest first move: rotate-holdout cross-val. Carried as a known caveat into Phase 3; confirm whether it actually costs notes against game score before treating it as blocking.

- **Need a real self-play capture to close the Phase-1 gate.** The exporter is verified against synthetic records, but the rollout's Phase-1 "done when" requires inspecting one real captured-gameplay CSV. Required record types in the capture's `PERF_CMD_SET_TYPE_MASK`: `SESSION` + `ACTUATOR` + `FRETBOARD_RAW` (the exporter strictly needs only these three); `DETECTOR` recommended for cross-checking `pressed_mask` vs `intended_mask`. The existing files in [`tools/marvin-perf/captures/`](../../marvin-perf/captures/) are *already-exported detector CSVs*, not raw `.bin` captures, so they can't be re-exported through the actuator path — a fresh raw capture is needed.
- **Corpus for Phase 2.** Many songs **at Expert** (single difficulty — see decision log), one held-out song reserved and reused across iterations so per-iteration metrics are comparable.

- **[RESOLVED 2026-08-03] Label↔feature pairing crosses two USB directions.** Distinct from the timestamp-burstiness issue above. The old `--labels=actuator` path forward-filled `PERF_REC_ACTUATOR` (timestamped when marvin *sends*) onto `FRETBOARD_RAW` (timestamped when marvin *receives*) as if they shared a clock, but the two streams travel opposite directions over USB CDC with independent jitter — an unknown, independently-varying skew (~12 ms / ~3 samples near command transitions).
  - **Fix (shipped):** the fretboard frame now carries `commanded_mask` — marvin's CV command, latched into the same 240 Hz frame as the ADC scan via the `0x88B9` teacher opcode `0x04`. `(sensor, label)` is captured atomically on-device, no cross-stream join, zero skew. marvin stays the teacher; we read its command off the wire at the point of truth. Export with `--labels=commanded-fb` (schema v6); the loader prefers it over the old actuator join. See fretboard/marvin journals 2026-08-03.

- **[CONFIRMED] Legato fret-hold was the fret-accuracy ceiling.** marvin's timing pipeline suppresses a fret release whenever a queued upcoming note needs that fret ([timing_pipeline.c:263](../../../firmware/marvin/default/src/actuator/timing_pipeline.c#L263)) — so across consecutive same-fret notes it holds the fret continuously, and in the gap the photosensor reads bright while the label stays `1` (driven by marvin's note-queue lookahead, not observable from the photo). **Proven by the `--labels=detector-fb` probe** (detector `pressed_mask` frets = clean per-note structure, no legato): on slowride-hard overfit, frets went **0.94→0.99 across the board** and the green→orange gradient flattened (loss 0.13→0.063); strum unchanged (same source). Sustains are safe under a line-263 change because a sustain holds via continuous detector `pressed` (no release edge), never reaching the suppression.
  - **But detector-fb is a probe, not the deployable label:** detector `pressed` (y=311) leads the photo dip by ~20 ms and releases ~220 ms *before* the strum, so a model trained on it would release the fret before strumming. Correct *structure*, wrong *timing*.
  - **Deployable fix (implemented 2026-06-03):** gated line-263 change in marvin's `timing_pipeline.c` — release a fret between separate notes, hold only when re-needed at/before its scheduled release (back-to-back); sustains untouched. Reflash **marvin only**, re-capture hard, export `actuator-fb` → expect ~0.99 deployable frets at correct strike-line timing. (No fretboard/wire change; `applied_mask` still == the command because there's no lazy actuator yet.)

- **[Decided] Final actuation architecture: released commands + lazy fretboard + log the command.** For good play at higher difficulties we want (1) marvin/model to command *released-style* per-note play (clean labels — done via line-263), and (2) a fretboard **lazy actuator** that physically holds a fret across same-fret gaps (releases only on a different non-empty fret command or a no-activity timeout) so fast Expert runs don't thrash release/repress and sustains aren't dropped (a dropped sustain makes the on-screen bar disappear → corrupts the feedback loop). Because the lazy layer makes physical state ≠ command, the training label must then be the **commanded** byte: when lazy lands, add a `commanded_mask` field to the fretboard frame/record (the reserved byte absorbs it; frame 17→18 B, schema v5) and the exporter sources `actuator-fb` labels from it. **Sequencing:** line-263 now (hard mode, `applied_mask` already == command); lazy actuator + `commanded_mask` together as the Expert follow-on. Strum mechanisms (monostable + threshold + weight) already validated — onset p95 ~16.7 ms, clean uniform pulses, glitches→0; recall/precision knee to be set on the consistent line-263 dataset (bias toward recall).

- **[Future] 3-state fret actuator (user idea).** Give each fret three states instead of two: *pressed-and-note-active*, *pressed-but-between-notes* (legato hold), and *released*. Would let the label distinguish "this fret is down because a note is here now" from "down only because it's reused soon" — directly encoding the legato hold rather than hiding it. Could be a cleaner supervision target than collapsing to a binary press. Parked until the detector-fb probe tells us whether the binary clean-structure label is enough.

- **[Future] Dedicated fret-line (scroll-speed) sensor.** The game highway's bar/measure lines scroll past a fixed point at a frequency that *is* the scroll speed — a direct observable of the one variable (difficulty/scroll-speed) that single-row note sensors can't see. A 6th ADC channel aimed at a column where only the horizontal fret lines pass (not the colored notes) would give the model an explicit scroll-speed signal, potentially letting **one** model generalise across difficulties instead of needing per-difficulty models. Open question whether a tiny model can actually exploit it to adjust strum timing. Pairs with [`review.md` Q1/Q5](review.md) (sensor count/placement). Flag for later; v1 stays Expert-only with the existing 5 channels.

- **Measure the photo→strum lag before fixing the window length.** With difficulty fixed, the lag is a constant we can measure (cross-correlate photo dips vs strum events in the real capture) rather than guess. Sizes the causal window precisely and turns [`review.md` Q3](review.md) from a blind sweep into a measurement + a narrow sweep around it. Lag-measurement utility is part of the Phase-2 package.

- **[Deferred — not fixing now] Fretboard ADC samples carry no true sample timestamp.** The first real self-play capture ([`tools/marvin-perf/captures/web-20260603-104406.csv`](../../marvin-perf/captures/web-20260603-104406.csv), 251.5 s, 59 958 rows) shows the per-row `timestamp` is **bursty, not uniform 240 Hz**: ~2.9 samples cluster within <0.05 ms, then a >10 ms gap (≈12 ms burst period), with *no* rows near the expected 4.17 ms spacing. Cause: `FretboardRaw.hdr.ts_counter` is stamped at marvin's USB-CDC RX/emit time, not at the fretboard's physical sample instant; the host receives the stream in bursts and the RX task drains buffered frames back-to-back.
  - **Consequences:** (1) row-index windowing is mandatory (see decision log); (2) forward-filled command labels can skew by up to one burst (~12 ms / ~3 samples) near command transitions — same effect as the "CDC + RTOS jitter in labels" risk in [`review.md`](review.md); measure its magnitude in Phase 2.
  - **Candidate fix (deferred):** have the fretboard MCU stamp each 12-byte data frame with its own sample-time counter and carry it on the wire, so marvin records the *absolute sample-time truth* instead of RX time. That's a fretboard wire-format + firmware change (and a `FretboardRaw` schema add on marvin) — out of scope for now. **For the moment we proceed assuming regular 240 Hz intervals and window by row count.** Revisit if Phase 2 shows the label skew hurts strum-timing accuracy.
