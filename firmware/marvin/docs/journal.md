**2026-07-10 — score + streak readers rewritten to integer math; fixed a coverage out-of-bounds bug (pending build).** Converted the shared coverage pipeline (luma → ink threshold → grid resize → per-cell coverage) in `gameplay_score.c` to pure integer so the firmware reproduces the host prototype **bit-for-bit**. This directly cuts hardware misreads: the device was extracting coverage in float32 while templates were built/validated in float64 (plus different rounding modes), so its reads diverged from what was validated. Now luma = `B*29+G*150+R*77` (no /256), ink threshold = rational `GP_{SCORE,STREAK}_INK_NUM/DEN` of the min..max range (`DEN*(luma-lo) ≷ NUM*(hi-lo)`), integer `gp_edge`, integer coverage; no float in the readers (ARM926 has no FPU). **Also fixed a real OOB bug**: when an ink bbox is smaller than the glyph grid, the last cell's block ran past the bbox and read the unused tail of the scratch buffer (stale data) → wrong coverage on short glyphs; clamped `yb→rh`/`xb→rw` to match the host (numpy) slice. Cross-check is now strict bit-exact (presence + every digit + every confidence flag). Digit banks in `gameplay_metadata.h` rebuilt with integer coverage. Files: `game/gameplay_score.c`, `game/gameplay_metadata.h` (regen). The multiplier (colour counts) was already integer. **Pending Greg's MPLAB build.** See gameplay journal 2026-07-10.

**2026-07-10 — gameplay_engine: streak tracker debounce + plausibility clamp (pending build).** Fixed a reported streak **lock** and two failures it surfaced, all in `gp_streak_track` (host-proven, see gameplay journal 2026-07-10). Over the capture: 0 implausible jumps, max 304, anchors exact; host suite 74. Still open: units-9 detection (needs more units exemplars — corpus-growth pass next). **2026-07-10 — gameplay_engine: note-streak reader (odometer OCR + confident-read tracker) → dashboard STREAK label (pending build).** Last scoring-block value after score + multiplier. The streak is a 3-tumbler odometer (note icon + hundreds/tens/units) that only appears at ~25+ and whose wheels *roll* — the units constantly, tens/hundreds at carries — so any frame can show unreadable wheels. Proven host-side (`tools/gameplay`, see its journal 2026-07-10) then ported.
- **Stateless read (`gp_read_streak`, `gameplay_score.c`, pure/cross-checked).** **Presence = the odometer is *locked at its final position*, detected from the note icon — not the digits** (Greg): the counter slides in from the bottom, overshoots, and bounces down to settle (`score-0335.png` = reference locked frame), and mid-slide the cells are misaligned → garbage. The fixed gold note glyph is a position fiducial — its coverage matches the locked template (L1 < `GP_STREAK_NOTE_MAX_SAD`) only when settled, cleanly rejecting both absent and slide/overshoot frames. When locked, three fixed cells (units dark-on-light, tens/hundreds white-on-dark) → 16×10 coverage → integer-L1 argmin over a **per-polarity 0-9 bank**; a wheel failing the gate is flagged unreadable. Fills `{present, digit[3], known[3]}`. Data frozen into `gameplay_metadata.h` (`GP_STREAK_*`: note template + two digit banks + ROIs + thresholds) by `gameplay export-c`. ROIs are absolute (fixed rig; chrome registration exists but is unused in v0).
- **Stateful tracker (`gp_streak_track`/`gp_streak_reset`, state owned by the caller).** **Presence is binary — not present ⇒ streak reset ⇒ 0** (immediate; the sole reset path). While present, **a confident wheel read is authoritative for its place** (Greg: a clear digit read trumps the rollover logic) — it wins even if the value drops, so a misread is a self-correcting one-frame blip; an unreadable (rolling) wheel is filled (holds last, or resets to 0 when a higher place carried). ≥2 confident wheels seed. This replaced a monotonic forward window `[last, last+30]` whose forward-only search couldn't represent a value below `last` → a tens misread locked the value high (11x read as 14x…); confident-trumps fixes it. Host validation over the 6549-frame capture: hand-read anchors exact (100 % in-sample confident-digit accuracy with the refined 8×15 cells), 0 non-reset decreases, correct slide-gating, max 304.
- **Engine + dashboard.** `game_state_t.streak` (new `uint16_t`); the observer holds one tracker (`s_streak`), advances it on `in_song` reads and resets it when gameplay is left; log adds `streak<s>`. Feed applies `DASH_EVT_STREAK` → `ScreenDashboard_ApplyStreak` → `Marvin_LABEL_DASHBOARD_ROBOT_Streak` via a fixed `leFixedString` (shows "0" at reset — see the 2026-07-10 label-clear fix).
- **Reset behaviour (w/ Greg).** Score/multiplier/streak zero out **the instant a run is requested** (top of `run()`, before nav/connect), not on reaching gameplay. During the song a **broken streak** (odometer no longer locked) blanks immediately (→ 0). **After the song ends everything stays** (score/multiplier/streak persist on the end screen) — the next run's request is the only reset. `play_until_done` tracks **peak streak** (persists across misses) + **final score** and logs `GC: result score N, peak streak M` — the values `Results_Append` (spec §4.8.6) will persist once that path is wired.
- **Known follow-ups (deferred, this commit lands the lock fix first):** (1) **Tens 0↔8 flicker** — the odometer's zero has a center slash; A2D aliasing closes its top loop on ~half the frames, so a tens "0" genuinely matches the **8** template better (4590 vs 6885) and reads 8 *confidently*, alternating frame-to-frame (100↔180, etc.; a hundreds variant flashes 900). Real per-frame ambiguity, not a template bug → fix with a **per-place debounce** (a changed confident digit must persist ≥2 reads before committing; can't lock since it follows reads up or down). (2) **Integer-coverage rewrite** — coverage is still float, so the per-wheel `known` flag can differ C-vs-Python on a borderline wheel (Python `np.round` half-to-even vs C half-up), benign for the tracker; going integer (midpoint threshold + integer grid edges) removes all FP (ARM926 has no FPU) and gives bit-exact parity.
- Host cross-check (`test_firmware_classify` `streak`): C == Python on presence + confidence flags + every confident digit, all 47 corpus frames; `test_streak.py` covers the tracker logic. Full gameplay suite **71 passed**; `gameplay_score.c` compiles clean under `cc -Wall -Wextra` via the cross-check driver. Files: `game/gameplay_score.{h,c}`, `game/gameplay_metadata.h` (regen), `game/gameplay_engine.{c,h}`, `game/game_controller.c`, `ui/dashboard_feed.c`, `ui/screens/dashboard/screen_dashboard.{c,h}`. No MCC/Legato hand-edits. **Pending Greg's MPLAB build + hardware validation** (streak label tracks the odometer, holds through single rolls, jumps at carries, blanks at song start / on a miss). Career-font score mode is the only deferred scoring-block item.

The renamed detail labels (Title/Artist/Album/Genre/Tier/Duration/Status) already used stable `LABEL_DASHBOARD_SONG_*` names, so only the new widgets needed wiring — dashboard code had no references to the removed decorative names.
- **Both time markers are runtime `leFixedString`s** (set up in `song_detail_init` alongside the Status label). `STOP_TIME` tracks the committed selection: `ScreenDashboard_ApplySelection` rewrites it with the song's `m:ss` (same `SongDetail_Duration` string shown in the DURATION field), "-" when unknown. `START_TIME` counts up with elapsed play time (see below); it resets to "0:00" on a fresh selection.
- **Bar fill + elapsed marker = playthrough time.** New feed event `DASH_EVT_PLAYTIME` (`u.play_ms`) + `DashboardFeed_PostPlaytime`. `game_controller.c` `play_until_done` posts `0` at play start (resets bar + marker) and elapsed ms each `GC_PLAY_POLL_MS` (~300 ms) poll. The dashboard consumer calls `ScreenDashboard_ApplyPlaytime`, which clamps elapsed to `s_song_len_s` (captured in ApplySelection), rewrites `START_TIME` as `m:ss` (formatted directly so 0 reads "0:00" — `SongDetail_Duration(0)` gives "-"), and drives the bar at **pixel resolution** via `ProgressBarAA_SetPermille` (0-1000) rather than the stock 0-100 `setValue` (unknown duration → empty bar, un-clamped marker). The 0-100 value quantized the 349px-wide bar to ~3.5px steps — for a long song it held still several seconds then hopped; permille advances it by single pixels.
- **Rounded (pill) bar ends.** New custom widget `ui/widgets/progressbar_aa/` (`ProgressBarAA_EnableRoundImage`) mirrors `panel_aa`: copies the *full progressbar vtable* (so `setValue` etc. survive), overrides `_paint` to run `AaCorners_RenderRoundImage` after the normal draw — eating the four corners back to the card's `SCHEME_PANEL_GRAY_18181B` BASE (resolved at paint time in the active mode). Radius 4 = half the 8px height → full capsule; the fill's leading cap rounds with it (interior pixels preserved). **The radius is carried by the AA pass, not the widget `cornerRadius`:** the stock classic skin's `drawFill` is a plain square `RectFill`, but its `drawBackground` switches to `FillRoundCornerRect` (ArcFills that overshoot the rect — a track visibly taller than the 8px fill) as soon as the widget `cornerRadius` is nonzero. So the widget keeps `cornerRadius` 0 (stock draws a plain square 8px track) and the AA pass owns the rounding. `ScreenDashboard_Setup` also pins the height to 8 (`setSize`, width preserved via `getWidth`). Added to `cmake/marvin/default/user.cmake`.
  - **Two-vtable gotcha (why the override first did nothing):** unlike a plain panel (where `panel->fn` *is* the base `widget.fn`), `leProgressBarWidget` holds two pointers to its vtable — its typed `bar->fn` and the base `bar->widget.fn`. The renderer dispatches paint via the *base* `widget.fn->_paint` (it works on a `leWidget*`), so `ProgressBarAA_EnableRoundImage` must repoint **both**; repointing only `bar->fn` leaves the stock paint running and the corners square.
  - **Partial-repaint gotcha (fill-end artifacts):** `AaCorners_RenderRoundImage` re-blends existing pixels toward the backdrop and writes at full-rect coordinates via `_Unsafe` pixel ops (relative to the current frame/damage rect, no bounds check). `panel_aa` is safe because a panel repaints its whole rect. But the stock `setValue` damages only the delta strip between old/new value, so a mid-bar update leaves the frame rect a sliver — the corner writes land outside that tile (garbage) and, over many updates, erode the AA bands into the fill (visible in the first/last ~10%). Fix + smoothness in one: the bar is no longer driven by the stock value at all. `ProgressBarAA_SetPermille` stores a 0-1000 fill fraction and invalidates the *whole* widget; `aa_paint` lets the stock skin draw only the (square) track — the widget value stays 0 so the stock fill is skipped — then draws the fill itself as a `RectFill` of the exact pixel width, then rounds the corners. Full-widget repaint every change keeps the corner writes in-bounds and idempotent, and the pixel-width fill removes the 100-step quantization.
- **Tier string is stars-only** (separate ask): `SongDetail_TierText` drops the " TIER n" suffix — main-setlist songs show just ★×tier, bonus still "BONUS". Shared helper, so song-select dialog and dashboard both change.
- Rides the existing single-consumer/render-lock feed flow — no off-thread widget touch. **2026-07-05 — `detect_active` no longer burns CPU while the source is dark.** Follow-on to the `cpu%` work below: VideoTask's active-area detector re-scanned the frame border **every 20 ms tick** while unlatched, and each *failed* scan (dark border) walked the whole band on uncached DDR (~2.6 ms) → ~13% whenever the source was dark (notably: booting while the Wii is asleep). Two fixes, and crucially **it still never gives up** — abandoning detection would permanently mis-frame a source that starts dark and later brightens:
- **Rate-limit:** `detect_active` self-caps to `VIDEO_ACTIVE_SCAN_MS` (100 ms, ~10 Hz) while unlatched instead of every tick. Trade-off: 16-frame accumulation now takes ~1.6 s after the source brightens (was ~0.3 s) — full-frame fallback shows briefly on wake, then snaps to the crop.
- **Dark-gate:** a cheap `frame_has_light()` (coarse grid, stride 64, returns on first bright sample) runs before the heavy border scan; an all-dark frame skips it → ~0 cost. So an asleep/dimmed Wii = near-idle, and detection resumes automatically the instant it brightens. Files: `video/video.c`. Build clean.

**2026-07-05 — Dashboard live-telemetry feed: fret activity → dashboard, single-consumer event flow.** The dashboard ROBOT fret buttons were static; wired them to track the actual guitar mask, structured as the general flow that score/multiplier/streak will also ride. New `ui/dashboard_feed.{c,h}`: a **single tagged event queue** (`dashboard_evt_t` = {type, union}) with **one consumer task** (prio 2, UI band) that blocks on the queue, coalesces last-per-type on drain, and applies to widgets. Design decided w/ Greg:
- **Hard constraint honored:** the actuation path (timing/gameplay/fretboard link) must never be delayed. Producers post with `xQueueSend(…,0)` (non-blocking, drop-on-full) — `FretboardLink_Send` (the convergence point for all producers) gets one `DashboardFeed_PostFret(v)` line, mirroring its existing `Fauxmote_SendGuitarMask` fan-out. One store-class op, no lock, no Legato touch.
- **Consumer is the sole dashboard widget writer, under a render lock.** Legato here is **single-threaded** — no `LEGATO_USE_OSAL`, no renderer lock, no `leTimer`; `_LEGATO_Tasks` runs `leUpdate` (events + one-pass paint) then `vTaskDelay(10ms)`. So *any* widget/damage edit from another task races the renderer. **First cut got this wrong** (consumer mutated widgets from its own prio-2 task): frets never showed and the SONG card updated one selection behind — the classic dropped-damage signature — and it likely contributed to a hard freeze. Fix: `UiManager_RenderLock()/Unlock()` — suspend `LEGATO_Tasks`+`SYS_INPUT_Tasks` and gate on `leRenderer_IsIdle()` (reliable now that scratch is sized to one full-screen pass, §13), so the edit can't corrupt an in-flight paint. The consumer wraps its coalesced apply in it. Held ~microseconds; never touches the actuation tasks (prio 4–5). Note this corrected a wrong assumption in an earlier draft of this entry that the old off-thread path was safe — the old `dash_selection_changed` actually ran **in-context** (from the SELECT button callback inside `leUpdate`), which is why it worked.
- **Same-class pre-existing race also fixed:** `dash_game_status` wrote the Status label from the game-controller task (prio 4) via `lestring_set_utf8` → `setFromChar`, which **does** invalidate — an off-thread invalidate that fires during gameplay (NAVIGATING→PLAYING…) alongside the fret traffic. Routed it through the feed too (`DASH_EVT_STATUS`, string copied into the event; `ScreenDashboard_ApplyStatus`). No off-thread invalidate remains.
- **Fret visual:** the classic skin fills a button with `LE_SCHM_BACKGROUND` when pressed (state ≠ UP) and `LE_SCHM_BASE` when up, so each fret scheme already encodes lit/unlit — no new schemes. Two non-obvious requirements to make it show (both needed): (1) the buttons must be **toggleable**, else `setPressed(TRUE)` just fires a click and leaves state UP; (2) **explicit `invalidate`** after `setPressed`, because `setPressed` only self-invalidates for image/bevel/pressed-offset buttons — for a plain scheme-filled button the UP↔TOGGLED colour swap wouldn't repaint. `ScreenDashboard_ApplyFret(mask)` does both, per bit (`TIMING_BIT_*`), touching only buttons whose state changed (cached `s_last_mask`); buttons also set `IGNOREEVENTS` (status display, not input).
- **Lifecycle:** `DashboardFeed_Init()` (queue) pre-scheduler in `UiManager_Initialize` so producers can post immediately; `DashboardFeed_Start()` (task) at end of `ui_boot_task` (post-reveal), so the consumer never touches the widget tree during build/paint/reveal. **2026-07-02 — Root cause of "NAND boot produces a non-working app": marvin outgrew the bootstrap's copy window + a flasher erase bug.** After recovering the board (entry below), the real question remained — why does `program-nand.sh` yield a broken app while `load-ram.sh` runs marvin fine? Two coupled defects, both triggered by app growth:

1. **App exceeds the bootstrap's fixed copy window.** The NAND/QSPI at91bootstraps (`*_uboot` defconfigs) copy a compile-time `CONFIG_IMG_SIZE` bytes from `0x40000`→`0x23F00000` and jump — no size header. Stock is `0x100000` (1 MiB, sized for u-boot). `out/harmony.bin` is now **`0x13f948` (1.25 MiB)**, so the bootstrap copied only the first 1 MiB → truncated marvin. `load-ram.sh` is immune (loads the whole ELF over JTAG). This is *what changed*: marvin crossed 1 MiB.

2. **Flasher erase undershoots the app.** `nand_console.py` program mode hard-coded `nand erase 0x0 0x100000`, but writes the app across `0x40000 … 0x40000+APP_SZ` (=`0x180000` now). Pages past `0x100000` were written onto **un-erased** NAND → corrupt → `PMECC: failed to correct corrupted bits!` (the error from the recovery saga). This bit once the app passed `0x100000-0x40000 = 0xC0000` (768 KiB); it was intermittent because a prior chip-erase leaves those pages `0xff`.

**Fix (all three coupled pieces must cover the app):**

**2026-07-02 — NAND recovery from a partial flash: two bugs fixed in the OpenOCD flashing tooling.** A board with a *valid* boot-region at91bootstrap but a *corrupt* app (`harmony.bin` at NAND 0x40000, `PMECC: failed to correct corrupted bits!`) loops forever (RomBOOT → bootstrap → app-load fail → RomBOOT), and `erase-nand.sh` couldn't get u-boot up to erase it. Two distinct defects:

1. **DDR-cold branch never used adaptive clocking.** `erase-nand.cfg`'s bootstrap-none path resumed the init-and-stop bootstrap at a fixed TCK, so OpenOCD lost JTAG sync when `lowlevel_clock_init` switched the master clock — `wait_halt` caught a garbage state (`ThumbEE`, `pc 0xfffffff9`, MMU on) → u-boot load aborted at `0x23f00000`. `load-ram.cfg` documents `adapter speed 0` (RTCK) as mandatory here; the DDR-cold branch was under-tested (only the DDR-up/marvin-running path had been exercised). Fixed by mirroring load-ram's `adapter speed 0` + `reg cpsr 0x000000d3` before the bootstrap resume.

2. **Double DDR init corrupts the MPDDRC (halfword shift).** Even with (1) fixed, u-boot loaded but never ran — total console silence. A DDR write/read probe showed a systematic **2-byte (one 16-bit halfword) shift**: `deadbeef 12345678` read back as `5678dead …`; u-boot's `ea0000b8 e59ff014` vectors read back as `f014ea00 …`, so the core fetched garbage as its first instruction. Root cause: the looping NAND bootstrap **already initializes DDR3L** (it must, to copy the app to `0x23f00000`), and `erase-nand.cfg`'s PC-based heuristic mis-classified it as "DDR cold" (the bootstrap is caught in **SRAM**, `pc 0x301068`) and ran bootstrap-none, whose DDR init re-trained an already-live MPDDRC → mistrained. **Verified**: probing DDR right after `reset init` *without* bootstrap-none read back clean (`deadbeef 12345678`). Fixed by replacing the PC test with a direct DDR round-trip probe — reuse existing DDR when the probe passes, run bootstrap-none only when it fails. Erase then succeeded (`nand erase.chip`, boot region all-`0xff`).

Also **hardened `program-nand.cfg` + `program-qspi.cfg`**: their guard only bailed on PC-in-DDR (marvin running), so a looping partial bootstrap (caught in SRAM, DDR up) would slip past and hit the same double-init. Added a DDR probe (only when caught in SRAM/ROM, to avoid poking a running marvin's MMU-mapped memory) so they now bail with "run ./erase-nand.sh first" in that case too. These staging tools still require **cold** DDR (they stage into low DDR a live capture DMA would clobber) — the fix is a better guard, not DDR reuse. Cold path verified; the looping-bootstrap detection is inferred from the erase-nand proof, not independently run (NAND is now erased). `load-ram.cfg` left unguarded (its contract is "no bootable medium").

Open follow-ups: (a) if `reset init` ever catches the NAND bootstrap *mid*-DDR-init, the probe reads shifted → falls through to bootstrap-none → double-init again; the real fix there is an MPDDRC reset before bootstrap-none (not built — no repro yet). (b) `program-nand.md:57` still says "JP3 (NAND-CS) may be either way for programming"; a manually-booted u-boot reported `no devices` with JP3 OUT, so that note is suspect — needs a clean JP3-OUT test before correcting.

| 2026-06-28 | **Config/operator settings (backlight %, mode toggles, calibration) persist to the onboard QSPI NOR (`SST26VF064BA`, 8 MB / 64 Mbit SQI) via flash EEPROM-emulation — a small wear-leveled ring-log, NOT a filesystem.   6. **`FreeRTOSConfig.h` — `portCONFIGURE_TIMER_FOR_RUN_TIME_STATS` / `portGET_RUN_TIME_COUNTER_VALUE` macros + 64-bit counter type.** With `configGENERATE_RUN_TIME_STATS = 1` (set via `FREERTOS_GENERATE_RUN_TIME_STATS` MCC symbol), FreeRTOS expects the application to provide a free-running counter. MCC's FreeRTOS Harmony component does not expose a knob for an app-specific counter source. Append at the end of `FreeRTOSConfig.h` (just before `#endif`):
     ```c
     extern uint64_t SYS_TIME_Counter64Get(void);
     #define configRUN_TIME_COUNTER_TYPE             uint64_t
     #define portCONFIGURE_TIMER_FOR_RUN_TIME_STATS()
     #define portGET_RUN_TIME_COUNTER_VALUE()        SYS_TIME_Counter64Get()
     ```

### 2026-07-01 — UI first-touch lag after screen change: paint canvases once at boot, make show/hide repaint-free

Greg noticed a ~0.5–1 s lag on the **first** touch after a "screen change" (open/close nav drawer, open song-select then tap a song); after that first tap, touch is snappy again.

**Root cause (traced through the Legato core).** Legato refuses to dispatch touch while its renderer is busy: `handleTouchDown` (and up/move) return `LE_EVENT_DEFERRED` when `leIsDrawing()` (`legato_input.c:396`), and `leEvent_ProcessEvents` leaves a deferred event queued to retry on the next `LEGATO_Tasks` tick (10 ms). A screen transition kicked off a large repaint that held the renderer non-idle for many ticks, so the first tap in that window was deferred repeatedly → the lag. The transitions repainted for no good reason: each screen renders into its own RAM canvas surface, and Legato paints into a canvas independent of its shown/bound (`active`) state (`gfx_canvas.c` `SET_ACTIVE_LAYER` succeeds for any canvas), so showing a painted screen should be a pure HW-layer bind.

**Three repaint sources removed.** (1) `navigation_open()` did an explicit `Marvin_PANEL_NAVIGATION->fn->invalidate()` on every open (full 320×800 repaint). (2) `songsel_set_input()` toggled `setEnabled()` on the dashboard + song-select panels for **modal input-gating**, but `_leWidget_SetEnabled` invalidates whenever the enabled state changes — so opening repainted the modal panels and closing repainted the whole dashboard. (3) nav open/close toggled `setEnabled(PANEL_DASHBOARD)` the same way → dashboard repaint on nav close.

**Fix.** Added `panel_set_pickable(leWidget*, leBool)` in `ui_manager.c` that toggles `LE_WIDGET_ENABLED` directly on `wgt->flags` — the renderer never reads ENABLED, and `leUtils_PickFromWidget` descends only into ENABLED children, so this gates a panel's whole subtree from picking with **zero** repaint. Exposed `UiManager_SetDashboardPickable(bool)` so nav and song-select share one dashboard gate. Reworked `songsel_set_input` onto it. In `screen_navigation.c` dropped the `invalidate()` and swapped the dashboard `setEnabled` calls for the gate. Added `paint_all_screens_once()` (invalidate dashboard/nav/song-select/album-art) called in `ui_boot_task` right before the existing `wait_render_idle()`, so every canvas surface is fully painted behind the splash and is never repainted on show again. Removed the now-redundant one-time `invalidate()` at the end of `ScreenSongSelect_Setup`.

**Why the old startup paint "didn't fully land"** (the comment that motivated the per-open invalidate workaround): MGS builds `PANEL_NAVIGATION` with `setVisible(FALSE)`, so `leAddRootWidget`'s boot root-damage painted nothing inside the drawer until `ScreenNavigation_Setup` later flipped it visible — fragile/incidental. The explicit `paint_all_screens_once()` makes it deterministic. Verified single-buffering (`bufferCount==1`, `LE_PREEMPTION_LEVEL==0`) so one drained invalidate lands a surface completely.

**Left intact:** content-change repaints — album-art swap on song tap (`setImage`) and nav highlight (`setScheme`) — are legitimate and unchanged. Rejected `LE_WIDGET_IGNOREPICK` for the gate (it still lets a panel's children be picked). The heavy 508×208 RGBA8888 album-art alpha blit is noted as a separate perf item.

**Status:** builds clean (XC32 v5.10, ninja). **Pending Greg's on-hardware check** that first-tap latency is gone on nav open/close, nav-close→dashboard, song-select open, song tap, and song-select close→dashboard. ### 2026-07-01 — Video-collapse recovery: watchdog (task #1) + blank HEO/BASE behind modal (Phase 2) + 594 Mbps lane rate (task #2)

**Task #1 — capture stall-watchdog (confirmed recovering on hardware).** New `capture_watchdog()` in `video.c`, called each video-task tick after `reconcile()`: while `s_capture_armed && s_capture_enabled && TC358743_IsLocked()`, it watches `ISC_Capture_FrameCount()`; if the count hasn't advanced for `VIDEO_STALL_TIMEOUT_MS` (500 ms) it logs a `LOG_WARN` and cycles the chain (`capture_disarm()` → `capture_arm()`), which re-runs `DRV_CSI2DC/CSI/ISC_Configure` and re-inits/re-locks the D-PHY once the bus is quiet. Timing via `xTaskGetTickCount()`; state is two function-static locals (`last_count`, `last_advance_tick`). Self-healing without spam: (a) when not actively capturing the reference is held fresh so a fresh arm gets a full window; (b) `ISC_Capture_Configure` zeroes `g_frame_count`, so after each re-arm the reference re-reads from 0 → a stuck source retries at most once per 500 ms window, not every tick. On hardware the watchdog fires and re-locks, but it fires on **every song switch** (log shows `capture stalled … re-arming` on each select) — recovery works, but the ~0.5–1 s freeze each time is a visible glitch. That motivated Phase 2.

**Task #2 — CSI-2 lane rate 972 → 594 Mbps/lane: TRIED, REVERTED (hypothesis wrong).** Theory was FIFO underrun: the bridge was hard-wired to 972 Mbps/lane (`tc358743.c PLL_FBD=144`) but the source is 720×480p60 (~27 MHz pixel clock, ~250 Mbps/lane needed), and the kernel `tc358743.c` `fifo_level` comment warns that when "CSI reads out faster than the data is arriving" it's underrun-prone → a GFX/DDR perturbation tips it → RX lanes to LP-11 (STOPSTATE=0x3). So I dropped to **594 Mbps** (kernel's characterized 2-lane default; the only lower timing set Linux fully tabulates): `PLL_FBD` 144→88, the nine TX timing `*_VAL` macros → kernel `case 594000000`, `ISC_CAP_CSI_BITRATE` 0x0A→0x07 (Gen3 band 550–600 from `dw-dphy-rx.c range_gen3[]`). **On hardware this made things worse:** boot now failed to hold lock and the watchdog re-armed 5–6× (stalled at frames 161/152/114/7/19) before finally catching a stable lock; reboot reproduced it. At **972** boot had been rock-solid (only the dialog stalled, now fixed by Phase 2). So on *this board* the 972 lane rate locks the D-PHY RX far more reliably at boot than 594 — boot-time lock margin dominates over any steady-state FIFO-underrun benefit. Briefly reverted to 972, then **re-examined** — Greg pushed back (rightly): a slower PHY clock should lock *more* easily, so "594 is just worse" is not an explanation. Clarified symptom: at 594 the frame counter advanced (frames arriving) but the **picture rolled/stuttered** and only turned clean after several re-arms, then stayed stable — i.e. **marginal data-sampling** (byte slips shifting the raster), not lock-loss. Root-cause dig (see also the code comments in `isc_capture.c`/`tc358743.c`): the RX rate knob is a single per-lane hsfreqrange code written by `plib_csi.c csi_phy_hs_rx_init` (plus a *fixed* `0x94` offset-cal validated at 972). Found **two disagreeing hsfreqrange tables**: Linux `dw-dphy-rx.c range_gen3` (594→**0x07**, 972→0x0A) vs the vendor `drv_csi.c CSI_BitRateLookUp` (594→**0x17**, 972→0x1A; vendor = Linux + 0x10 across bands). We used 0x07 (Linux); reality follows Linux at 972 (0x0A works) so 0x07 *should* be right — but 594 is far less forgiving of a near-miss. **hsfreqrange band ruled out (2026-07-01).** Tested 594 with 0x07 then **0x17** (vendor value); *no difference* — both flaky. So the RX band code is not the cause. Sharper symptom read with `VIDEO_STALL_TIMEOUT_MS`=100 ms: **each arm is bimodal** — the D-PHY locks, passes 1–30 frames, then the lanes collapse (watchdog re-arms); *most* arms collapse, but *occasionally* one lands a good calibration and then runs **stable for minutes**. So 594 steady-state is fine; only the **bring-up handshake/calibration is marginal and lands bad most tries**. Since RX band is out and the RX offset-cal (`plib_csi.c` fixed `0x94`) is rate-independent, the differentiator vs rock-solid-972 is **TX-side** (TC358743 CSI PLL at FBD=88/594 MHz, or the 594 D-PHY TX timing counts — esp. `LINEINITCNT` 0xE80 vs 972's 0x1B58, the LP-11 init window the RX must catch), or a PLL-settling race at EnableStream.

**Instrumenting the collapse (2026-07-01).** Added `ISC_Capture_DumpDiag()` (unconditional LOG_WARN variant of the DEBUG-gated `diag_dump_rx`; refactored both onto a shared `emit_rx_diag(tag, lvl)`), fired from `capture_watchdog` at each stall (first 8 only, to not flood UART) *before* the re-arm resets the latches — kept in place as a general stall diagnostic.

**Datasheet nailed the mechanism (2026-07-01 — Greg pointed at SAM9X75 DS §48.6.1.3 / §5.6.6.1.3 Analog Initialization).** Two facts: (1) the bit-rate table confirms **0x17 = 550–599 Mbps** (so our RX code is *correct*, and the vendor `csi_phy_hs_rx_init` matches the datasheet's test-code-0x44 procedure) — the RX band is definitively **not** the fault; (2) *"The initialization period … has a **minimum of 100 µs** … the D-PHY starts decoding low-power commands **after** the analog initialization."* The **RX** needs ≥100 µs to init/calibrate; the **TX** (TC358743) provides that window by holding the opening **LP-11 for `LINEINITCNT`** before the first HS burst. `LINEINITCNT` at 594 (`0xE80`) is much shorter than at 972 (`0x1B58`) — if it's too short the RX per-lane calibration lands *marginal*, giving the rolling picture, and only an occasional re-arm hits a good calibration → then stable forever (**exactly** the bimodal symptom). This is TX-side + rate-dependent, which fits: RX band ruled out, and 972 works because its `LINEINITCNT` window is long enough. **RESOLVED: 972 is the correct rate for this source; keep it (2026-07-01).** Web research (sourced from mainline `tc358743.c`, its header, the FIFO-374 patch, and RPi forum threads by the driver author) settled it: the **TC358743 has a single 512×32-word line FIFO and cannot rate-convert** — the CSI-2 output must drain faster than the HDMI fills. A 27 MHz-pixel 480p source is the *worst* mismatch (drain/fill 1.8× @594, 3× @972). **`FIFOCTL` (0x0006) is the trigger level in 32-bit words (0–511); there is no published formula** (Toshiba's REF_02 `.xls`), 374 is empirical. Crucially, **Raspberry Pi's universal default is 972 Mbps + FIFO 374** — they run 972 for everything and don't fight 594; our working config mirrors theirs exactly. Our `ErrSotSyncHS` is a D-PHY HS-lock failure (not a clean FIFO underflow); the kernel's **594 TX timing counts are marked FIXME/approximate**, and 972's are better-conditioned for this TC358743↔SAM9X75 pairing. **No 594 erratum, no hsfreqrange band-boundary defect** (that hypothesis had zero support). Conclusion: 972 is not a fallback — it's the right operating point for a low-pixel-clock source on this bridge, and the "combined config that works" is the one we already have (972 + FIFO 374 + the 972 timing set). Reverted all three files to 972 / 0x0A / 972-timing. The stall-diagnostic (`ISC_Capture_DumpDiag`, first 8 stalls) is left in as a general D-PHY stall tool; `VIDEO_STALL_TIMEOUT_MS` left at Greg's 100 ms. Task #2 closed — the marginality it aimed to reduce is already gone at 972 (watchdog + Phase 2).

**Rate is not the lever (2026-07-01).** Data points now: 972 = clean/stable; 594 = ErrSotSyncHS, ~1–30 frames/attempt; 540 (FBD=80, band 0x07, FRS=0) = **same ErrSotSyncHS signature**, ~7–173 frames/attempt (marginally longer, so *not* monotonic "lower=worse"). Every sub-972 rate fails identically (`PHY_FATAL=0x3`, `PKT_FATAL=0x1`, `CSI_PHY_RX=0x00030000` invariant); only 972 works. So the working point isn't about bandwidth (540 is ample for 480p's ~324 Mbps/lane need) — something makes only the ~972 region lock reliably. Prime remaining un-validated knob: **FIFOCTL** (see below); research agent still out on the formula + the known-480p issue.

**TC358743 TX config faithfully matches the kernel's proven 594 setup (2026-07-01).** Compared our `tc358743_set_csi()` register-by-register against Linux `drivers/media/i2c/tc358743.c` `tc358743_set_csi()`: CTXRST reset, unused-lane disables (D2W/D3W for 2-lane), all 9 PPI timing counts, HSTXVREGEN (CLM+D0M+D1M), TXOPTIONCNTRL=CONTCLKMODE, STARTCNTRL, CSI_START, and CSI_CONTROL (CSI_MODE|TXHSMD|NOL_2) + err/int enables — **all identical**. PLL (FBD=88→594) and timing counts match the kernel `case 594000000`. So we are *not* missing or misprogramming a TX register; our 594 config is the kernel's known-good 594 config. The **one** setting the kernel author explicitly punted on is **`FIFO_LEVEL` (FIFOCTL, hardcoded 374)** — their comment says it should be computed from input/output data rates but the formula is "buried in Toshiba's REF_02 spreadsheet." That's the prime remaining suspect for a **480p-specific (low ~27 MHz pixel clock)** failure. Greg's recollection: TC358743 is reportedly known-bad with 720×480@60 in Linux (which defaults to 594) — so 972 working for us may be *the* right config for a low-pixel-clock source, not a mere fallback. Launched a web-research agent to find the FIFOCTL formula + the known 480p issue + whether a higher lane rate is the accepted workaround.

**`LINEINITCNT`=0x1B58 did NOT help — but the stall dump nailed the failure class (2026-07-01).** Every collapse dump is identical: `CSI_INT_ST_PHY_FATAL=0x3` (**ErrSotSyncHS on both data lanes**), `PKT_FATAL=0x1` (**header ECC double-bit error**), `STOPSTATE` 0x3→0x0, CSI2DC/ISC otherwise idle+armed (`GSR=0`, `DCTRL=1`). So the RX *does* enter HS (SoT detected — not the 80–110 default, not TX-stopped) but **mis-samples the HS bits** → can't sync the leader byte → ECC-garbage headers. It's a bit-sampling failure. Combined with 0x07≡0x17 (the two bands program *different* THS-SETTLE, yet behaved identically ⇒ settle/band is **not** the dominant error), the other half of the SoT handshake is implicated: the **TX HS timing** (`THS_HEADERCNT` = THS-PREPARE/ZERO) that the RX settle races. Kernel counts: 594 → `0x0103` (prepare=3/zero=1), 972 → `0x0806` (prepare=6/zero=8). At 594 prepare-cnt 3 ≈ 40 ns ≈ *under* the MIPI THS-PREPARE min (~47 ns) → RX can't lock the SoT. **Fix under test:** run 594 rate (`FBD=88`) + 0x17, but with the **full 972 TX timing set** (prepare=6/zero=8, LINEINITCNT 0x1B58, etc.) — longer, known-good-on-this-link, and the lengthened prepare stays under the MIPI max at 594's slower byte clock. Diag dump still armed. **Awaiting hardware.** If clean → the aggressive 594 counts were it; narrow to `THS_HEADERCNT` and compute proper 594 values. If still ErrSotSyncHS → the mis-sample is independent of TX timing (byte-clock/skew at 594, or a CSI/CSI2DC rate assumption) and 594 likely isn't viable via this vendor driver → stay at 972.

**Phase 2 — blank the video (HEO) + discard BASE behind the modal (confirmed on hardware).** Root of the per-switch stall: the album-art RGBA8888 decode/blit + repaint on each selection is a heavy DDR burst that, layered on top of HEO's 720×480×3×60 read and BASE's full-panel read, knocks the marginal D-PHY out of lock. **Per-selection blit: use `LE_IMAGE_DIRECT_BLIT` (the cover slots set it).** First cut had a visible hesitation on each song selection — the cover was being re-blitted **per-pixel in software**. Cause: `leGPU_BlitBuffer` sets `SRC_OVER` blend whenever the source is an *alpha mode* (RGBA8888 always is, regardless of actual opacity — `LE_COLOR_MODE_IS_ALPHA`), and the GFX2D driver's blit only implements `PLIB_GFX2D_Copy` (returns `GFX_FAILURE` for any blend), so `leGPU_BlitBuffer` fails and the RAW decoder falls back to its per-pixel software stage over all 508×208 px. Covers are opaque + fill the widget, so the overwrite is correct; labels still composite on top. Removes the hesitation.

**GPU blit not reachable without a driver change (noted, not done).** Confirmed the cover can't be true-GPU-blitted as-is: `DRV_GFX2D_Blit` returns `GFX_FAILURE` for every non-NONE blend and never wires `PLIB_GFX2D_Blend`, so the GFX2D driver does **zero** hardware blending — *all* alpha-blended blits in the UI silently fall to CPU, not just covers. Reachable only by forcing NONE for opaque RGBA8888 (loosens the global `IS_ALPHA` test — risky) or implementing `SRC_OVER` via `PLIB_GFX2D_Blend` in the driver (the right, general fix; candidate second Microchip bug alongside the PNG one). Not worth it for a one-shot per-selection copy — left on `_directBlit`.

### 2026-06-30 — UTF-8 for dynamic strings (song-select + song-list)

Non-ASCII chars in dynamically-set labels were rendering as two glyphs each. Root cause: Legato decodes UTF-8 only on the *string-table* path (`leDecodeCodePoint` keyed off the table's `encodingMode`, which we switched to UTF-8 in MGS). Fixed/dynamic strings have no encoding mode — `setFromCStr` and the C-string renderer (`drawCString`) are byte-oriented: each UTF-8 byte becomes its own `leChar`/glyph. `leChar` is `uint16_t`, so strings are really UCS-2 code-point arrays.

Fix: new shared helper `default/src/util/legato_utf8.{c,h}` — `utf8_to_lechar()` decodes a UTF-8 C string into a `leChar` buffer via `leDecodeCodePoint(LE_STRING_ENCODING_UTF8, …)`; `lestring_set_utf8()` wraps it + the base `setFromChar` vtable call (works for any fixed/dynamic string). Song-select detail labels now use `lestring_set_utf8` instead of `setFromCStr`. The song-list widget renders rows through the C-string renderer, which can't be made UTF-8-aware, so `draw_str` now decodes into a stack `leChar` buffer and renders via `leStringRenderer_DrawUString` (the leChar-buffer path; alignment logic is identical to the C-string path). BMP-only (code points >U+FFFF truncate) — fine for song metadata. Not yet confirmed on hardware.

### 2026-06-28 — QSPI settings store (EEPROM-emulation ring-log) built + stress-validated

`flash/settings.{c,h}` implements the persistent operator/UI settings store over the `QSPI_SETTINGS_*` region (16 KiB / 4 sectors → 64 page-slots). Each record is a 256-byte page slot `{magic, seq, settings_t, crc32}` (CRC over magic..data). Boot scans all 64 slots and picks the highest-`seq` CRC-valid record (else compiled defaults); `Settings_Save()` appends to the next slot and erases a sector only when crossing into it — always ahead of the live record, so it's **power-fail safe** (a torn write fails CRC → previous record wins) and **wear-rotated** (~1 erase per 16 saves, alternating sectors). Bitwise CRC-32, static scratch buffers, bounded synchronous polling (safe pre-scheduler). Payload `settings_t` = `{version, backlight_pct, reserved0}`, extensible via `version`. `settings` console command: `dump`/`save`/`wipe`/`stress [n]`/`backlight <pct>` (applies live + persists). **`settings stress` PASS at 200 and 1000 saves** — wipes, saves N (recomputable values), then reloads from flash and verifies the highest-`seq` record matches the last write; confirms ring wrap + sector erase never clobber the live record. Note: `qspi` smoke/`verify` write the same region (CRC-fallback-to-defaults makes that non-fatal). **Wired into boot (confirmed on hardware — backlight survives power-cycle):** `enable_backlight()` lights the panel at `Settings_Get()->backlight_pct` (lazy-loads the ring; compiled default 50% if no record — the hardcoded `BACKLIGHT_DEFAULT_PCT` in `ui_manager` is removed), and the `backlight <pct>` console command applies live + persists. First QSPI consumer is live; splash-blob + DMA load is the remaining one.

### 2026-06-28 — QSPI read throughput: clock fix + XDMAC mem2mem (18.2 MB/s, integrity-verified)

### 2026-06-27 — Backlight: GPIO → PWM dimming on PC18 (50% default)

**Duty direction (SAM PWM gotcha):** SAM PWM `CDTY` is the time spent at the **`CPOL` level**, not absolute high-time. ### 2026-06-26 — Splash bring-up #3: garbled splash root-caused to the XLCDC per-layer color-mode gotcha
